Everything about PID assumes the problem can be reduced to one error signal and one corrective response. As long as the system fits that shape, PID works remarkably well.

The system in this article does not fit that shape.

## The Hidden Assumption

Every PID controller is built around the same loop, it measure an output, compare it to a reference and apply a correction. One error in, one control signal out.

Buried inside that structure is an assumption so common it usually goes unstated: the controller is only dealing with one thing at a time.

For something like motor speed control, that's perfectly fine. The error is one-dimensional, the input is one-dimensional, and the interaction between them is simple enough that reacting directly to error works well.

But not every system shares that shape.

## A Pendulum Standing on Its Head

A cart sits on a horizontal track. A pole is hinged to it at the base — not hanging downward, but balanced upright, like a broomstick on a palm. The only control input is a horizontal force applied to the cart.

The goal: keep the pole upright while controlling where the cart sits.

_Can we just run two PID loops?_

One controller watches the pole angle and moves the cart to keep the pole balanced. Another watches the cart position and drives the cart back toward the center, both operate simultaneously, each correcting its own error signal.

The problem appears immediately.

Correcting a rightward lean in the pole requires pushing the cart left. But moving the cart left creates position error, so the second controller pushes right to correct it — which disturbs the pole again.

The loops are not independent. Every correction in one introduces error into the other. They are not solving the problem in parallel but are fighting each other.

Increasing the gain on either loop makes this worse. More aggressive correction means faster interference. The system begins oscillating, or the pole falls entirely.

The issue is not that PID can never stabilise the system. The issue is that the coupling has to be managed indirectly through careful architecture and tuning because the controller itself has no representation of the coupled state. This is a structural limitation.

## What PID Cannot See

PID has no model of the plant it's controlling. It doesn't know that pushing the cart affects the pole. It doesn't know that the pole angle and cart velocity are related through the physics of the system. It sees one number and reacts to it, blind to everything else.

For the cart-pendulum, the state of the system at any moment is not one number. It is four:

$$x = \begin{bmatrix} x \\ v \\ \theta \\ \omega \end{bmatrix}$$

These four quantities evolve together, coupled through the nonlinear equations of motion. What happens to $\theta$ depends on $v$. What happens to $v$ depends on $\theta$ and $\omega$ simultaneously.

A controller that only sees one of these at a time is working with an incomplete picture. Not incomplete in a correctable way. Incomplete in a way that is baked into its architecture.

## Seeing the Whole State

Instead of asking _what is the error in this output_, we should ask _what is the full state of the system, and where do we need it to go_.

This is the state-space framing. The system is described not by a single output and a single error, but by a vector $x$ containing every variable needed to predict the future evolution of the system. The controller's job is not to react to one error signal but to drive the entire state vector to a desired equilibrium.

For the cart-pendulum, equilibrium is the state where all four quantities are simultaneously zero: cart at the origin, stationary, pole upright, not rotating. Getting there requires a controller that sees all four variables and acts on them together.

The control law takes a form that is structurally different from PID:

$$u = -K(x - x_{eq})$$

$K$ is not a single gain. It is a vector of four gains — one for each state variable. The control input is a weighted combination of all four states simultaneously. How much the cart's current velocity matters. How much the pole's angular velocity matters. How much each deviation from equilibrium contributes to the corrective force.

_Where do the weights come from?_

## The Cost of Control

This is where LQR earns its name.

LQR stands for Linear Quadratic Regulator.

_Linear_ refers to the model of the system: a linearised approximation of the dynamics around an equilibrium point.

_Quadratic_ refers to the cost function being minimised.

_Regulator_ refers to the objective: driving the state toward equilibrium.

The important idea is the cost function itself.

Control is always a tradeoff. A controller can stabilise the system aggressively, using large control inputs to settle quickly. Or it can act more conservatively, using less force but taking longer to converge.

LQR makes that tradeoff explicit.

Instead of tuning gains by hand, a cost is defined over time: penalise the system for deviating from equilibrium, and penalise the controller for using excessive input.

The weighting matrix $Q$ determines how much different state errors matter. Larger values in $Q$ mean the controller cares more strongly about keeping those states near equilibrium.

The matrix $R$ penalises control effort. Larger $R$ means the controller becomes more conservative about applying force.

Once the model and cost weights are specified, the mathematics produces the optimal gain matrix $K$.

<Callout type="insight">
  LQR doesn't just stabilise the system. It stabilises it optimally, in the
  precise sense that no other linear controller with the same cost weights can
  do better.
</Callout>

This is the thing PID cannot do. PID has no model of the plant, no notion of coupled state, and no cost function describing what tradeoffs matter.

It reacts to error.

LQR optimises behaviour.

## The Pendulum, Revisited

The [simulation in this repository](https://github.com/cyriacus73/nonlinear-pendulum-lqr) starts with the pole slightly disturbed from vertical — a small push, the kind that would send a hand-balanced broomstick to the floor.

The LQR controller receives the full state vector at each timestep and computes a single force on the cart that accounts for all four states simultaneously. The cart moves but the pole doesn't fall. All four states converge.

_A pendulum standing on its head — and staying there._

What makes this possible is not just the control law but the step before it: the nonlinear equations of motion were linearised around the upright equilibrium, and that linearisation required computing the system's Jacobian — the matrix of partial derivatives describing how each state affects every other near a given point. Without it, the linear model doesn't exist, and neither does the LQR design.
