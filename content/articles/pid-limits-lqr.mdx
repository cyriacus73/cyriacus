A PID controller knows nothing about the system it controls. It doesn't need to. It sees one number — the error — and it reacts. For everything we built in the last two articles, that was enough.

It won't be enough here.

## The Hidden Assumption

Every PID controller is built around a loop: measure one output, compare it to one reference, produce one corrective input. The assumption embedded in that structure — so natural it rarely gets named — is that there is only one thing to care about at a time.

This is not a flaw. For a motor holding a speed, it's exactly right. The error is one-dimensional, the input is one-dimensional, and the coupling between them is the only coupling that matters. PID was built for this shape of problem, and it handles it well.

But the shape doesn't hold in general.

## A Pendulum Standing on Its Head

A cart sits on a horizontal track. A pole is hinged to it at the base — not hanging down, but balanced upright, like a broomstick on your palm. Your only input is a horizontal force on the cart.

The goal: keep the pole upright while controlling where the cart sits.

_Can we just run two PID loops?_

One loop watches the pole angle and pushes the cart to correct it. Another watches the cart position and drives it back to center. Both running simultaneously, each doing its job.

The problem reveals itself immediately. To correct a rightward lean in the pole, the first loop pushes the cart left. But moving the cart left disturbs the cart position, which the second loop then corrects by pushing right — which disturbs the pole again. The loops are not independent. Every corrective action in one creates an error in the other. They are not solving the problem in parallel. They are fighting each other.

Increasing the gain on either loop makes this worse. More aggressive correction means faster interference. The system doesn't converge — it oscillates, or it falls.

The issue is not that PID can never stabilise the system. The issue is that the coupling has to be managed indirectly — through careful architecture and tuning — because the controller itself has no representation of the coupled state. The failure is structural.

## What PID Cannot See

PID has no model of the plant it's controlling. It doesn't know that pushing the cart affects the pole. It doesn't know that the pole angle and cart velocity are related through the physics of the system. It sees one number and reacts to it, blind to everything else.

For the cart-pendulum, the state of the system at any moment is not one number. It is four:

$$x = \begin{bmatrix} x \\ v \\ \theta \\ \omega \end{bmatrix}$$

These four quantities evolve together, coupled through the nonlinear equations of motion. What happens to $\theta$ depends on $v$. What happens to $v$ depends on $\theta$ and $\omega$ simultaneously.

A controller that only sees one of these at a time is working with an incomplete picture. Not incomplete in a correctable way. Incomplete in a way that is baked into its architecture.

## Seeing the Whole State

The shift required here is not subtle. Instead of asking _what is the error in this output_, ask _what is the full state of the system, and where do I need it to go_.

This is the state-space framing. The system is described not by a single output and a single error, but by a vector $x$ containing every variable needed to predict the future evolution of the system. The controller's job is not to react to one error signal — it is to drive the entire state vector to a desired equilibrium.

For the cart-pendulum, equilibrium is the state where all four quantities are simultaneously zero: cart at the origin, stationary, pole upright, not rotating. Getting there requires a controller that sees all four variables and acts on them together.

The control law takes a form that is structurally different from PID:

$$u = -K(x - x_{eq})$$

$K$ is not a single gain. It is a vector of four gains — one for each state variable. The control input is a weighted combination of all four states simultaneously. How much the cart's current velocity matters. How much the pole's angular velocity matters. How much each deviation from equilibrium contributes to the corrective force.

_Where do the weights come from?_

## The Cost of Control

This is where LQR earns its name.

LQR stands for Linear Quadratic Regulator. The _linear_ refers to the system model — a linearised approximation of the plant dynamics around the equilibrium point. The _quadratic_ refers to the cost function — the quantity being minimised. The _regulator_ refers to the goal — driving the state to zero.

The cost function encodes a tradeoff: how much do you care about state error versus how hard the controller has to work? A controller that corrects aggressively uses a lot of input but settles fast. One that is gentle uses less input but takes longer. LQR finds the gain matrix $K$ that minimises the total cost over time — the integral of state error and control effort, weighted by two matrices you choose:

$Q$ penalises state error. Larger $Q$ means the controller cares more about how far the states are from equilibrium. $R$ penalises control effort. Larger $R$ means the controller is more conservative about how hard it pushes.

You set the tradeoff. The mathematics then produces the optimal gain matrix $K$.

<Callout type="insight">
  LQR doesn't just stabilise the system. It stabilises it optimally, in the
  precise sense that no other linear controller with the same cost weights can
  do better. The gains are not tuned by hand — they are derived from the physics
  of the system and the cost you specify.
</Callout>

This is the thing PID cannot do. Not because it's less sophisticated — but because it has no cost function, no model of the plant, and no mechanism for trading off state errors against each other. It reacts to one signal. LQR reasons about the whole system.

## The Pendulum, Revisited

The [simulation in this repository](https://github.com/cyriacus73/nonlinear-pendulum-lqr) starts with the pole slightly disturbed from vertical — a small push, the kind that would send a hand-balanced broomstick to the floor. The LQR controller receives the full state vector at each timestep: cart position, cart velocity, pole angle, angular velocity. It computes a single force on the cart that accounts for all four simultaneously.

The pole doesn't fall. The cart doesn't drift. All four states converge to zero.

_A pendulum standing on its head — and staying there._

What makes this possible is not just the control law but the step before it: the nonlinear equations of motion were linearised around the upright equilibrium, and that linearisation required computing the system's Jacobian — the matrix of partial derivatives describing how each state affects every other near a given point. Without it, the linear model doesn't exist, and neither does the LQR design.
